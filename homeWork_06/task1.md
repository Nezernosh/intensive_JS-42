#### DRY
DRY — основополагающий принцип разработки. Он расшифровывается как Don’t repeat yourself — «не повторяйтесь».

Когда пишете код, всегда думайте о том, как можно переиспользовать тот или иной фрагмент, что можно выделить в универсальную функцию или класс, сделать модулем. При этом речь не идёт о создании библиотек под каждую неодноразовую функцию — имеется в виду очень похожая логика, которая встречается в нескольких местах, которую, возможно, есть смысл вынести в функцию. А если в нескольких местах определена одна и та же функция, то её можно вынести в общий модуль. Ну и, наконец, если вы часто используете один и тот же модуль, вероятно, из него можно сделать библиотеку.

Другими словами, don’t repeat yourself.

Этот принцип полезен всегда, вне зависимости от платформы или языка. Допустим, вам надо автоматизировать некое поведение. Чтобы не прописывать несколько раз одну и ту же логику и не раздувать код без нужды, попробуйте обобщить её и вынести в отдельный элемент.

В большинстве случаев дублирование кода происходит из-за незнания системы. Прежде чем что-либо писать, проявите прагматизм: осмотритесь. Возможно, эта функция где-то реализована. Возможно, эта бизнес-логика существует в другом месте. Повторное использование кода – всегда разумное решение.  

#### KISS
Keep it simple, stupid («Сделай это проще, тупица») или, если кому-то не нравится называться тупицей, есть вариант Keep it stupid simple («Пусть всё будет простым до безобразия»), который ещё лучше передаёт смысл аббревиатуры.

Решая какую-нибудь проблему, можно так увлечься, что сам не заметишь, как уже занялся оверинжинирингом, вовсю палишь из пушки по воробьям. Задача в итоге, конечно, будет решена — но её можно было бы выполнить куда проще и изящнее.

Бывают, конечно, и обратные ситуации. Слишком простой код или простая архитектура могут оказаться неэффективными, и тогда в логику придётся добавлять чуть больше сложности. Но всё равно надо каждый раз себя спрашивать, соблюдается ли принцип KISS.

Проверяйте, достаточно ли понятны ваши логические цепочки. Хватит ли знаний вашим коллегам, чтобы в них разобраться? Простой код и простой дизайн уменьшают риск ошибок, да и читать такой код проще. В общем, не забывайте про KISS!  

Одна из самых распространенных ошибок нашего времени – использование новых инструментов исключительно из-за того, что они блестят. Разработчиков следует мотивировать использовать новейшие технологии не потому, что они новые, а потому что они подходят для работы.  

#### YAGNI
Принцип, иначе известный как You ain’t gonna need it («Вам это не понадобится»). Согласно ему создавать какую-то функциональность следует только тогда, когда она действительно нужна.

Дело в том, что в рамках Agile-методологий нужно фокусироваться только на текущей итерации проекта. Работать на опережение, добавляя в проект больше функциональности, чем требуется в данный момент, — не очень хорошая идея, учитывая, как быстро могут меняться планы.

Итерации в Agile довольно короткие — то есть вы будете получать какой-то фидбэк уже на ранних этапах разработки, и потенциально он может изменить направление всей работы над проектом. Так зачем вам тратить время на функцию, которая в итоге окажется совершенно ненужной?

Однако, если вы используете методы каскадной разработки, где вся работа планируется заранее и все стараются чётко придерживаться плана, принцип YAGNI неприменим.

Этот принцип также применим при рефакторинге. Если вы занимаетесь рефакторингом метода, класса или файла, не бойтесь удалять лишние методы. Даже если раньше они были полезны – теперь они не нужны.

Может наступить день, когда они снова понадобятся – тогда вы сможете воспользоваться git-репозиторием, чтобы воскресить их из мертвых.  

#### Антипаттерны

Антипаттерны — это распространенные решения, которые кажутся эффективными, но на практике приводят к проблемам в коде. В контексте чистого кода антипаттерны нарушают принципы читаемости, поддержки и расширяемости.

##### Глобальные переменные

Использование глобальных переменных увеличивает вероятность конфликтов имен и затрудняет отслеживание изменений состояния.

```javascript
// Глобальная переменная
var userName = 'John Doe';

function greet() {
    console.log('Hello, ' + userName);
}

greet();
```

Глобальные переменные могут быть изменены из любого места в коде, что затрудняет отладку и понимание логики программы.

##### Спагетти-код
Код с запутанной структурой, где функции и логика сильно взаимосвязаны без четкой организации.

```javascript
function processData(data) {
    // Много вложенных условий и циклов без четкой структуры
    if (data) {
        for (let i = 0; i < data.length; i++) {
            if (data[i].active) {
                // Обработка активных элементов
                console.log(data[i].name);
            }
        }
    } else {
        console.log('No data');
    }
}
```
Трудно читать, поддерживать и тестировать такой код из-за отсутствия четкой структуры и разделения обязанностей.

##### Жестко закодированные значения (Magic Numbers)

Использование "магических чисел" или строк без пояснения их значения снижает читаемость кода.

```javascript
function calculateArea(radius) {
    return 3.14159 * radius * radius;
}
```

Неясно, что представляет число `3.14159`. Лучше использовать константы с осмысленными именами.

```javascript
const PI = 3.14159;

function calculateArea(radius) {
    return PI * radius * radius;
}
```

##### Повторение кода (DRY Violation)

Повторение одинаковых или схожих фрагментов кода в разных местах программы нарушает принцип DRY (Don't Repeat Yourself).

```javascript
function getUserName(user) {
    return user.firstName + ' ' + user.lastName;
}

function getAdminName(admin) {
    return admin.firstName + ' ' + admin.lastName;
}
```

Код дублируется, что усложняет его поддержку и увеличивает вероятность ошибок.

```javascript
function getFullName(person) {
    return person.firstName + ' ' + person.lastName;
}

function getUserName(user) {
    return getFullName(user);
}

function getAdminName(admin) {
    return getFullName(admin);
}
```

##### Ненужная сложность (Over-Engineering)

Создание избыточных или ненужных структур и решений, которые усложняют код без реальной необходимости.

```javascript
// Использование сложной иерархии классов для простой задачи
class Animal {
    constructor(name) {
        this.name = name;
    }
}

class Mammal extends Animal {
    constructor(name) {
        super(name);
    }
}

class Dog extends Mammal {
    constructor(name) {
        super(name);
    }

    bark() {
        console.log('Woof!');
    }
}

const myDog = new Dog('Rex');
myDog.bark();
```

Избыточная иерархия классов усложняет код без добавления полезной функциональности.

```javascript
class Dog {
    constructor(name) {
        this.name = name;
    }

    bark() {
        console.log('Woof!');
    }
}

const myDog = new Dog('Rex');
myDog.bark();
```
